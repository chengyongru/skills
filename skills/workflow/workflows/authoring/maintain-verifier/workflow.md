# Maintain a verification skill

A feature map rots the moment the app changes. This skill is the upkeep loop for a skill generated by `$workflow create-verification-skill` (or any project-local verification skill with a feature map). The unit of rigor is the feature, not every sentence: cover every feature file from source and exercise every feature live, without terminalising every bullet.

## Outcomes

Pick one, and say which:

- **clean** — every feature got source and live coverage; nothing worth shipping. No branch, no PR.
- **changed** — proven doc, harness, or map corrections, applied only to an authorized standalone target or delivered as patch proposals for immutable package content.
- **blocked** — coverage could not finish or a proven fix could not ship safely. Say exactly what blocked it.

## Edit scope

An audit-only request stays read-only except for authorized disposable verification state. Apply corrections only when authorized, within a standalone verification skill at `<agent-workspace>/skills/<name>/` and its owned features/helpers. Use installed `skill-creator` and [repo-prose](../../writing/prose/workflow.md) when applicable. Packaged skills receive external patch proposals unless a plugin change was expressly requested; actual plugin changes require review and re-enabling after finalization. Never edit profile/memory/history files or product code during this pass. A missing behavior is either doc drift or a product regression; report the latter rather than weakening the journey.

## Pass

0. **Locate the target.** Find the installed verification skill with launch/drive sections and a feature map, normally `<agent-workspace>/skills/verify-<app>/SKILL.md` for an authored standalone skill. Use the matching project-specific verifier or [project adapter](../../../references/project.md), then [public-surface verification](../../verify/public/workflow.md). Several maintenance targets mean ask which; none means point at `$workflow create-verification-skill`, not invent one. Confirm writable ownership and the authorized live-test scope before continuing.

1. **Index hygiene.** Read the feature map README and discover siblings with `list_dir`/`rg --files`. Identify missing, extra, duplicate, or dead entries; apply only authorized corrections. Keep this lightweight, with no generated inventory.

2. **Source wave.** Assign one feature file per native child task in bounded waves, normally two at once, retaining returned task IDs. Each explains the feature from source, flags likely drift with citations, and returns one concise live recipe. Its explicit contract prohibits file edits, app driving, process launches, and external actions. Return shape: feature summary / source entry points / likely drift or none / one recipe. Children inherit the configured model. If delegation is unavailable or prohibited, read the same features directly and report the limitation.

3. **Reconcile.** Every feature file has a returned summary. Merge overlapping recipes into as few app states as practical. Spot-check cited drift; don't re-prove clean claims. Sweep recent churn for user-facing surfaces missing from the map — require a concrete source path before calling one missing.

4. **Live pass.** Required even when source looks clean. The coordinator owns all driving; follow the verification skill's own launch model — one long-lived instance driven serially for servers and UIs, or a fresh isolated session per drive for short-lived CLIs (the skill's Launch section decides, not this one). Exercise every feature at least once, and hold three invariants the whole pass, whatever the failure: (1) never drive an instance you haven't health-checked since it last did something surprising — doctor before first drive, doctor on each fresh session where sessions are the unit, doctor again after any failed drive, and where doctor can't see the failure (a wedged UI state on a healthy process), reset to a known state or relaunch rather than hoping; (2) evidence captured so far survives every cleanup, checked at its named location, not assumed; (3) nothing a drive started outlives that drive's usefulness — failed-iteration residue is cleaned whether the session is stuck, exited, or shared (for a shared instance, clean the residue, not the instance). A doctor failure caused by skill drift is drift: apply an authorized standalone fix, otherwise propose it and stop blocked; for an applied fix retry once — restart whatever the fix invalidated, nothing more — before calling the pass `blocked`. A feature that cannot be reached is `verified-unreachable` only with the concrete prerequisite (auth, entitlement, OS, external state) and route attempted; that label records the tested access boundary, not passing feature behavior. Missing permission or untested access is blocked, not verified. If the map omits a real prerequisite, that is drift. Any harness fix from triage gets re-driven live before it ships. Final teardown happens after the last drive of the run — including those re-proofs — so nothing outlives the run (evidence stays, per the skill).

5. **Triage.** Wrong or missing user-POV description → doc drift, fix it. Working behavior the harness can't drive → harness gap, fix it; a harness fix follows the same helpers rule as generation (scripts executable, invocation documented in the skill body). App behavior that's actually broken → product gap; record it for the user, keep it out of this PR.

6. **Deliver or stop.** Re-read every applied change or proposed patch. Report clean, changed, or blocked and the coverage honestly. Open/push a PR only if separately authorized; otherwise hand back local corrections or proposals. This pass does not create a schedule.

Keep concise run notes and evidence under a task-owned external directory, such as `<agent-workspace>/.nanobot-workflows/runs/<task>/`; do not commit them automatically. If the user asks for a maintenance cadence, use `cron` only after the actual interval and scope are explicit.
