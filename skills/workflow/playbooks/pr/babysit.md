### Babysit

**Own a bounded readiness pass, not the landing.** Start only for the user's requested status, triage, or fix scope. Opening a PR does not start babysitting. Shipping handles an explicitly authorized landing request.

1. **Declare the mode.** `check` is one read-only status pass for "is it green?" or "check X" and is the default when intent is unclear. `threads-only` investigates requested review threads, with fixes/replies only if authorized. `drive` works within the requested fix scope toward merge-ready during this session. A private `background` child, if useful and allowed, is a bounded task, not a persistent monitor. Do not turn a status question into edits.
2. **Identify the actual frontier.** For a stack, read the ordered PR/base/head chain and prioritize the lowest unresolved prerequisite. Record upper-link findings without rewriting the stack. Keep one active writer per branch and one readiness owner per stack; inspect known ownership before starting. Use installed [pr-worktree](../../workflows/pr/worktree/workflow.md) for any authorized fix work.
3. **Read GitHub state explicitly.** Use `gh pr view` for state, head/base, draft status, review decision, and mergeability; `gh pr checks` for current checks; and available `gh api` REST/GraphQL reads for review history and unresolved review threads, with pagination. Missing thread access or unknown mergeability is a limitation. No bundled watcher or forge-specific verdict strings are available. A green list does not prove required approvals, resolved blockers, or a mergeable integration result.
4. **Classify before acting.** Conflicts need an authorized branch/topology owner, not an opportunistic rebase inside babysitting. Triage review claims with the [review-claim triage](../../workflows/pr/review/references/bot-triage.md) against current code and head. Classify CI failures from logs as changed-code defects, base/integration defects, infrastructure, or uncertain. Unchanged files do not by themselves prove a stale base or a flake. A retrigger is a remote mutation: only if authorized, only after evidence justifies it, and bounded to avoid repeated blind retries.
5. **Fix only the owning scoped code.** For an authorized fix, reproduce a confirmed finding, add a red-first check where practical, and batch related corrections in the lowest unmerged owning unit. Do not silently create a follow-up PR when that owner already merged. Record the need and obtain the appropriate scope. Rebase, retarget, force-push, closing PRs, and changing protections are not babysitting defaults.
6. **Publish conditionally.** Commit/push, comment/review publication, and thread resolution each require coverage by the user's authorization. Otherwise draft the reply and report the evidence locally. For an authorized GitHub reply, use a body/payload file as data with `gh api`; never interpolate a review body into executable shell text. Do not resolve a security or data finding merely because a bot repeated it or a prior owner dismissed something similar.
7. **Recheck and stop honestly.** After an authorized change, reread the exact head and affected checks/threads. Stop at merge-ready, a user gate, pending external checks beyond the session budget, a real blocker, or the user's hold. Await bounded child completion notifications instead of tight polling; use `check`, `send`, and `cancel` on known IDs when needed and reconcile final writer/process state. If CI is still pending, report pending rather than keeping a sleeper alive or claiming green.

A request for future or recurring checks goes through `cron` at the user's requested cadence with a bounded prompt and stop condition. Do not install a schedule as a playbook step, start a sustained goal without Goal Runtime Guidance, or promise to survive this turn. Keep useful head-bound evidence and any checkpoint in `.nanobot-workflows/runs/<run>/`, outside the plugin. Propose reusable triage lessons there; do not edit the live shared rubric or private memory during babysitting.

**Reply:** mode, current frontier/head, checks and review/thread state, confirmed fixes versus drafted replies, unresolved gates, evidence paths, and whether the PR is ready, pending, or blocked. Babysitting never grants merge authority.
