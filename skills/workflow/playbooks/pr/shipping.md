### Shipping

**Land only the authorized, verified change at the head and base you inspected.** A readiness question gets a readiness answer.

1. **Establish the boundary.** Identify the repository, requested PRs, dependency order, and the user's landing scope. Read current state with `gh pr view` and `gh pr checks`; inspect required reviews and unresolved threads separately through the available GitHub API. Record head SHAs, bases, draft state, check results, mergeability, and any user-owned gates. A green check list alone is not merge readiness.
2. **Verify each unit at its actual artifact.** Inspect the diff and existing receipts; use installed [pr-review](../../workflows/pr/review/workflow.md) for review and the matching verifier for reachable changed behavior. Docs-only changes do not need invented UI/performance lanes. Missing live proof is WARN/blocked, not a pass.
3. **Reconcile drift.** Bind every verdict to head and base. A changed head, dependency, build configuration, caller, or merge result can invalidate prior evidence. Patch identity is a useful clue, not proof that a rebased artifact behaves the same. Preserve only checks whose inputs are demonstrably unchanged and explain that decision; rerun affected checks on the current artifact. If trunk changes can affect the patch, test the integration result in a safe owned worktree. Do not mutate a shared or dirty worktree to simulate a merge.
4. **Select a contiguous eligible run.** For a stack, start at the lowest unmerged PR and stop at the first missing verdict, unresolved gate, or missing authorization. A verified PR above an unverified dependency waits. An independent PR may move only through an authorized topology change and fresh affected verification. Write down the ceiling of this shipping pass before landing.
5. **Merge one eligible PR at a time, only if authorized.** Re-read head, base, checks, reviews, threads, and mergeability immediately before the action. Confirm the PR targets the intended destination, not an unmerged parent's branch. Use the repository's required strategy and head-match protection when supported by the installed `gh`. Do not bypass forge approvals, protection, or hooks. Do not arm auto-merge unless the user explicitly requested that mode; it can act on a later head and needs its own safeguards.
6. **Confirm the outcome.** Read the PR back with `gh pr view --json state,mergedAt,baseRefName,headRefOid,mergeCommit`. Queued or auto-merge-enabled is not merged. Record the actual merge result. If landing the next link requires retargeting, rebase, or a remote branch update, stop unless that operation is authorized. Have the single topology owner perform it, then refresh current-head checks and affected verification before the next merge. Never perform an automatic force-push as shipping bookkeeping.
7. **Stop at the ceiling or first new blocker.** Keep other writers off the chain during a landing operation. Diagnose a stall before changing topology or retrying. Monitoring is a bounded `gh` status pass in this session, not a watcher daemon. A user-requested future/recurring check uses `cron` at the requested cadence with a clear stop condition; do not schedule it automatically.

Keep head-bound evidence and a single-writer checkpoint under the agent workspace's `.nanobot-workflows/runs/<run>/`. If authorization ends at readiness, stop there and provide the evidence-backed recommendation.

**Reply:** inspected run and ceiling, each PR's current head/base and verdict, remaining gates, what actually merged and how confirmed, evidence paths, and the next gap. Distinguish ready, queued, and merged.
