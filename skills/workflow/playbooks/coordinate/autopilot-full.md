### Autopilot-full

**Carry independent units through build, review, and verification; land only what the user authorized.** Use this for independent changes that can be evaluated separately. A plan request is not a go, and the name "autopilot" grants no unattended runtime or remote permissions.

1. **Declare the contract.** Name the queue, exclusions, dependency order, acceptance criteria, finite session budget, and user-owned gates. List local editing, commit, push, PR, review-publication, and merge authority separately. Items outside that grant stop at local complete or merge-ready.
2. **Assign owners without multiplying shared state.** Use installed [pr-worktree](../../workflows/pr/worktree/workflow.md) to reuse one registered worktree per branch. Independent units branch from the agreed base; coupled units route to Autopilot-stack. Work directly when that is simpler, or create bounded native children with disjoint write scopes, normally at most two concurrently. A no-subagent request prevails. Each brief includes actual skill/reference paths, allowed actions, proof, report format, and a partial-report stop condition. Do not specify models or cloud placement.
3. **Build and checkpoint.** Each owner makes a focused change, inspects it, and uses installed [simplify](../../workflows/code/simplify/workflow.md) when appropriate. Run the repository's relevant checks and follow its formatting policy. Keep exact base/head, modified paths, evidence, and known child/process handles under `.nanobot-workflows/runs/<run>/`, outside the plugin. One writer owns each checkpoint; child reports have separate paths. Do not push merely to preserve work. Local files and an authorized commit can be the handoff.
4. **Verify the code-ready artifact.** Review actual receipts and the diff, not just the owner's summary. Use [pr-review](../../workflows/pr/review/workflow.md) for PR review and the target project's verifier or [verify](../../workflows/verify/public/workflow.md) for changed behavior. Select high-signal checks for the reachable change; no mandatory ten-worker, live, or performance lanes for documentation. Same-model review is labeled as such. If cross-model verification is an explicit acceptance condition, report it blocked without a supported interface.
5. **Fix forward within scope.** Send confirmed findings to the existing writer in one bounded batch. Reproduce the defect and add a red-first regression check where practical. Distinguish a new/reached regression from a pre-existing unrelated defect. Do not widen scope or weaken a gate to obtain a pass. A changed head gets fresh affected verification and current-head CI. Base drift is assessed for actual integration risk, not handled by automatic rebases.
6. **Deliver conditionally.** Follow Opening a PR only for authorized publication. An early draft PR can be useful when requested; it is not mandatory. Use `gh` for current status, including checks, review decisions, mergeability, and unresolved threads. Babysit is a bounded authorized pass, not an implied watcher. Only an explicitly authorized eligible merge routes to Shipping. No owner may infer merge or approval authority from a coordinator's clean verdict.
7. **Reconcile lifecycle.** Await child completion notifications while doing independent work. Use `check` on known tasks when needed; silence or an unchanged log is not proof of a stall. Diagnose a real failure before a bounded retry. Before replacing a writer, send a hold, cancel where necessary, and confirm its final task/process state. Do not overlap replacement writers. On the user's stop, stop dispatching and record each owned resource's state.
8. **Close or hand off.** Check the original goal against the real artifact, account for every owner, and report pending/blocked units. A checkpoint does not keep the program running. Only use `cron` when the user requests a time or cadence; sustained goals need Goal Runtime Guidance. Do not install an hourly audit, refresh instructions from moving trunk, or promise work after this session by default.

Keep a head-bound record of any gate decision. Required forge approvals cannot be countersigned away, and loosening budgets, disabling checks, or changing product expectations needs the appropriate user decision rather than an owner's desire for green.

**Reply:** each unit's state, base/head, verdict and evidence, any authorized PRs/merges, user-owned gates, limitations, and the external checkpoint path. State whether work ended or awaits a new turn.
