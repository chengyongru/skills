# Maintain formal verification

Use for `$workflow maintain-formal-verification-skill` or a request to check whether a model/proof still describes the code. A passing stale model is dangerous: it can verify an implementation that no longer exists. Scope edits to authorized verification files, not product code or the installed plugin. Audit-only requests return proposals.

1. **Find the named checks.** Read the verifier's property, code mapping, assumptions, bounds, command, and last synchronized source snapshot. Prefer existing repository checks; with none, point to [Create formal verification](../create-formal-verifier/workflow.md). If the sync record is absent, use the last verification-file commit as an explicitly provisional starting point and report the unknown earlier correspondence.
2. **Run the current check once.** Record the actual outcome before editing. A pass is a result about that model or harness, not evidence that it matches current code. Use [Statechart](../../verify/statechart/workflow.md) for TLA+ results. Unavailable required tooling remains blocked.
3. **Trace all relevant changes.** Inspect covered code from the sync snapshot to the current commit and dirty changes, following renamed, moved, split functions and new writers of the same state. Classify each change against the verification: no semantic effect; model/harness drift; an intentionally changed promise supported by user-confirmed requirements; or a possible violation. A commit message alone does not establish a new product contract.
4. **Update from code, not desired results.** Restore the action-to-code mapping and actual atomic boundaries. Preserve the property unless its intended contract changed; record old/new wording and the supporting decision. Preserve bounds unless the domain changed, and disclose any reduction. Never narrow the state space, add fairness, or weaken an assertion just to erase a failure.
5. **Rerun and challenge the result.** A passing updated check must still reject a relevant broken variant. For an abstract model, update the mutation's source mapping too; an unchanged model cannot detect arbitrary code edits. For a failure, replay the counterexample against real code. An impossible action is model drift; a reachable violation is a bug candidate, confirmed through the supported interface where feasible. Trace a regression to its introducing change. Keep product fixes outside this maintenance pass.
6. **Update the coverage record only for completed work.** Record exact checked commit/dirty hashes, covered symbols, assumptions, command, and evidence. Do not advance a blocked check's sync marker. Run the resulting verifier instructions once and preserve the evidence outside the plugin. Keep verification changes separate from any separately authorized product fix.

Per check, report **in sync**, **updated**, **bug**, or **blocked**. Updated and bug can both apply. Say when an old pass was on a stale description, identify the tested property and actual outcomes, and disclose unverified source correspondence or new uncovered paths. Do not replace a required runtime test with the model check, create a schedule, publish, or edit protected profile/memory files as a maintenance side effect.
