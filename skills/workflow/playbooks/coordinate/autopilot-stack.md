### Autopilot-stack

**Deliver a verified dependency chain for the user to review and land.** Apply Autopilot-full's scoped build, verification, checkpoint, and bounded-child discipline, but not independent-branch layout or any landing step. This playbook stops at stack-ready unless the user separately authorizes Shipping.

1. **Define the chain before writing.** Record each unit, parent branch, exact parent/head SHA, allowed paths, and proof. The root targets the agreed trunk; dependent work starts from its parent's actual branch/head. Use installed [pr-worktree](../../workflows/pr/worktree/workflow.md) to reuse one registered worktree per distinct branch. Do not create several worktrees for the same branch.
2. **Give topology one owner.** Unit owners change only their assigned code and report the intended parent and new head. One coordinator owns any authorized chain rebase, base retarget, or remote history update. Before changing a branch, stop and reconcile its code writer; a topology owner and worker must not write concurrently. No owner may infer permission to push, force-push, close, merge, or enable auto-merge from the stack plan.
3. **Verify each link, not only the tip.** Inspect the incremental diff against its parent and run the checks for its observable contract. Identify which evidence relies on unmerged lower links. Use matching installed verifiers and a bounded review scope.
4. **Handle drift deliberately.** Read current bases/heads with Git and, for existing PRs, `gh`. Determine whether parent or trunk changes affect a link. Rebase or retarget only when in scope, then rerun affected proof and current-head CI. Patch identity alone does not carry a verdict across changed dependencies. Never repair the chain by hard reset or an unapproved remote rewrite.
5. **Deliver only authorized artifacts.** If PR creation is authorized, follow Opening a PR: root targets trunk, each child targets its parent branch, and every PR records its actual verification and limitations. Otherwise deliver the local branch chain and evidence without publishing. Report STACK-READY only when every required link has current evidence and user-owned review gates are clearly identified.
6. **Freeze during landing.** Once the user starts a shipping pass, no other writer changes that chain. New findings go to the landing owner and wait for an explicit decision. Authorized post-merge retarget/rebase operations belong to Shipping and require fresh affected verification; they are not automatic stack maintenance.

**Choosing the autopilot:** Autopilot-full for independent units, with landing only if granted. Autopilot-stack for coupled or sequenced work and review-before-landing. Neither creates a schedule or a standing agent.

**Reply:** root-to-tip dependency order, branches or authorized PR links, each base/head and verdict, remaining review/publication gates, exclusions, and the `.nanobot-workflows/runs/<run>/` checkpoint/evidence paths.
