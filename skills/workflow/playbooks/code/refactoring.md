### Refactoring

**Own the contract. Structure changes; behavior does not.** Use installed [simplify](../../workflows/code/simplify/workflow.md) for focused behavior-preserving cleanup. A missing feature or real bug discovered during cleanup is a separate finding, not an automatic extension of the refactor.

1. Pin the behavior before moving structure. Read the affected subsystem and its callers, using [how](../../workflows/investigate/how/workflow.md) when useful. Prefer existing characterization tests, a recorded baseline, or a meaningful equivalence check. Add a focused pin when evidence is missing and writes are authorized. Typecheck/lint alone do not prove behavior unchanged, but every task does not require a new harness file.
2. Name the structural problem and target shape: fewer branches, fewer invalid states, clearer ownership, or less hidden state. Choose a data model that makes the logic simpler. For a consequential boundary change, explore the design with [architect](../../workflows/code/architect/workflow.md); do not add abstraction to already clear local code.
3. Subtract safely before adding. Remove proven dead code and redundant layers only after checking consumers and contracts. Keep required boundary validation, compatibility, and useful rationale. A speculative cleanup that adds risk without evidence does not stay.
4. Move in small steps with the pin green. For an internal API under coordinated control, migrate known callers and remove the old API in the same verified unit. Do not assume there are no external consumers or break shared/live states. Public API, schema, persistence, dependency, or UX changes need explicit scope and the corresponding migration plan.
5. Work directly or delegate mechanical edits in a bounded native child when permitted. Give exact names/paths, behavior to preserve, forbidden actions, and acceptance proof. Use installed [pr-worktree](../../workflows/pr/worktree/workflow.md), one writer per branch, and disjoint output paths. Do not require delegation or pass model/runtime fields. Check strings, documentation, and back-references as well as static references for renames.
6. Prove equivalence on the relevant artifact: old/new outputs under the same fixture, baseline replay, or a smoke scenario through the matching verifier. Use the target project's verifier or [verify](../../workflows/verify/public/workflow.md) when no more specific verifier applies. Record head/base, actual commands, outcomes, and limitations. A new head or changed dependency needs affected proof refreshed.
7. Confirm the result reduces reader load without removing behavior or safeguards. Revert only your own unnecessary changes, not a whole dirty worktree. Keep unrelated improvement ideas in the handoff.
8. If commits/history edits/publication are authorized, deliver coherent ordered slices with hooks intact and follow Opening a PR. Otherwise return the local diff and evidence. Do not rebase, reset, or force-push merely to make the refactor look clean. Follow the project's formatting policy.

**Reply:** structural change, pinned contract and equivalence proof, concrete reader-load improvement, limitations, delivery state, and anything deliberately excluded. No new behavior disguised as cleanup.
