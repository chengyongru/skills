### Hillclimb

**Own the metric, correctness floor, and bounded experiment.** Use this for a requested series of improvements to one measurable thing. A one-off fix is Bug fix or Perf issue. This playbook does not start a sustained goal without Goal Runtime Guidance.

Core discipline: one hypothesis, one change, one measurement, then keep or reject. Never stack untested changes or claim a win from inspection alone.

1. Ground the architecture and workload with [how](../../workflows/investigate/how/workflow.md). Name realistic dimensions such as data size, history, state, and concurrency. Reproduce the user's complaint before optimizing it. Fix the metric, desired direction, target, regression floor, and attempt/time budget using the user's numbers when provided. A minimum attempt count is optional and must serve the requested experiment, not an arbitrary ritual.
2. Use or build the smallest scoped measurement harness. Prove its sensitivity with contrasting realistic workloads, vet it with [benchmark-checklist](../../workflows/verify/benchmark/workflow.md), then freeze the workload/metric for comparable attempts. Report error and completed-work counts, repetitions and spread. Record baseline and green regression checks before implementation. Do not change the harness or relax a budget to claim a win; a necessary correction restarts the comparison with an explicit explanation.
3. Keep an external attempt record under `.nanobot-workflows/runs/<run>/`: hypothesis, exact base/head or dirty-snapshot state, change, before/after with units and noise, regression result, kept/rejected decision, and evidence. Run the shared [workflow helper](../../scripts/workflow.py) with `paths` to locate run state and `log <file> <phase> <decision> <why> <evidence> <result>` for a decision trail. Keep one writer per record and do not edit the plugin to store progress.
4. Ground each hypothesis in a mechanism, such as removing blocking work from first paint. For performance, use Perf issue's mantra order. Work directly or use a bounded native child when helpful and permitted. Competing hypotheses need independent registered branch worktrees, not concurrent writers on one branch. Default to a small fan-out, not an open-ended fleet; a no-subagent request prevails.
5. Measure before/after under the frozen workload and run the correctness floor. Keep a change only if improvement clears noise and behavior stays correct. A proven simplification that holds the metric may be worth keeping within scope; label it honestly rather than counting it as a speedup. Reject only your own experimental diff, preserving prior/user changes. Commit accepted units only if commits are authorized and stage intended paths, not the whole worktree.
6. At a plateau, review the evidence and try a bounded change of category when useful. Correctness and simplicity outrank the number. Stop at the agreed predicate, budget, user hold, missing capability/decision, or a documented diminishing-return/dead-end condition. Never relax the target or run indefinitely because cheap ideas might remain.
7. Follow Opening a PR only for authorized publication. Save a pickup checkpoint if work remains; private child IDs cannot be resumed after restart. A user-requested future/recurring attempt uses `cron` at the requested cadence with a bounded task and stop condition. Do not promise unattended life after this turn.

**Reply:** metric/workload and target, baseline → final with units and spread, percent delta when comparable, attempts kept/rejected, each accepted change, actual regression proof, evidence/record path, final predicate state, and the next useful idea if further work is requested.
